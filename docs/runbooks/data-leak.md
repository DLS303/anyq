# Утечка персональных данных

Регламент на случай признака того, что персональные данные пилотного
контура оказались у того, кому они не предназначались, или что секрет
приложения вышел за сервер. Это SEV1. Уровень и эскалация —
в [`deploy/INCIDENT.md`](../../deploy/INCIDENT.md).

Алерты приходят в любое время. Шаги человека выполняют в рабочие часы
(Asia/Almaty, UTC+5). Срок SEV1 считают в рабочих часах. Срок решения
собственника об уведомлении уполномоченного органа считают отдельно:
один рабочий день, см. раздел «Восстановление».

Регламент не описывает способ, которым данные могли уйти. В карточку
и в канал не кладут имена субъектов, контакты, секреты и журналы.

## Признаки

- Пилотный клиент или пользователь сообщает, что видит чужие данные.
- Секрет приложения оказался вне сервера и вне закрытого хранилища в Казахстане.
- Есть иной признак постороннего доступа к персональным данным. В канал пишут «есть признак», без подробности, которая сама содержит данные.

Пока признак не подтверждён и не снят, уровень остаётся SEV1.

## Первые 15 минут

Пятнадцать минут считают от момента старта срока SEV1 в
[`deploy/INCIDENT.md`](../../deploy/INCIDENT.md), внутри рабочего окна.
Юриста и собственника зовут в этом же окне: их срок не ждут до конца
восстановления.

1. Координатор (дежурный DLS) ставит SEV1 и открывает карточку по [`docs/incidents/TEMPLATE.md`](../incidents/TEMPLATE.md).
2. В карточку пишут два времени Asia/Almaty: когда появился алерт и когда человек увидел его в рабочем окне.
3. Эскалация по плану: IT/MLOps, разработчик приложения, SQL-разработчик, собственник, юрист.
4. Если доступ снаружи ещё может отдавать данные, сначала изолируйте вход. Журналы снимайте сразу после этого и до пересоздания контейнеров.
5. Клиенту в эти минуты не подтверждают и не опровергают утечку. Короткое письмо — только по [`docs/runbooks/comms.md`](comms.md) и только после одобрения собственника.

## Восстановление

Порядок такой: изоляция, сохранение следов, оценка категорий,
смена секретов приложения, решение собственника. Загрузка архива
поверх текущей базы на этом шаге следы уничтожает. `deploy/restore.sh`
— будет добавлено, `pgbackrest` — будет добавлено. Их не запускают,
пока координатор отдельно не запишет, что следы больше не нужны
и что это уже восстановление порчи, а не утечки. Откат выпуска,
если признак совпал с выпуском, — [`docs/runbooks/bad-deploy.md`](bad-deploy.md)
(`deploy/rollback.sh` — будет добавлено) и только после копирования журналов.

### Изоляция

Остановите внешний вход. API и PostgreSQL оставьте работать, чтобы
снять следы. Тома не удаляйте. Порты в compose-файле не меняйте.

```bash
cd /opt/anyq
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml stop caddy
```

Не выполняйте `docker compose down -v`, `docker volume rm` и не
чистите `/var/backups/anyq`.

### Сохранение следов

Каталог — в Казахстане, путь `<закрытый-каталог-инцидентов>/<номер>`.
Журналы могут содержать персональные данные. Их не коммитят и не
пересылают в канал. Копируют, а не перемещают.

```bash
mkdir -p "<закрытый-каталог-инцидентов>/<номер>"
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml ps \
  > "<закрытый-каталог-инцидентов>/<номер>/ps.txt"
docker logs anyq-api --tail 2000 \
  > "<закрытый-каталог-инцидентов>/<номер>/api.log"
docker logs anyq-caddy --tail 2000 \
  > "<закрытый-каталог-инцидентов>/<номер>/caddy.log"
docker inspect anyq-api \
  > "<закрытый-каталог-инцидентов>/<номер>/api-inspect.txt"
stat -c '%y %n' deploy/.env \
  > "<закрытый-каталог-инцидентов>/<номер>/env-mtime.txt"
```

`deploy/.env` в этот каталог не копируют. В файл времени попадает
только время изменения, не содержимое.

Существующие архивы в `/var/backups/anyq` не перезаписывают.
Новый `deploy/backup.sh` на этом шаге не запускают: он не нужен
для сохранения журналов и создаёт свежий дамп, который легко
перепутать со слепком на момент события.

### Чьи данные затронуты

SQL-разработчик считает категории, а не выгружает людей.
В канал и в карточку попадают названия коллекций и числа.
Не выполняют запросы, которые печатают `email`, `payload`,
`search_text`, `token_hash`, `company_bin` или содержимое коллекции
`credentials`.

```bash
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml exec -T postgres \
  psql --username anyq --dbname anyq -c \
  "SELECT collection, count(*) AS rows
   FROM records GROUP BY collection ORDER BY collection;"
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml exec -T postgres \
  psql --username anyq --dbname anyq -c \
  "SELECT count(*) AS invitations FROM invitations;"
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml exec -T postgres \
  psql --username anyq --dbname anyq -c \
  "SELECT count(*) AS photo_jobs FROM photo_jobs;"
docker run --rm -v anyq-data:/data:ro alpine:3.20 \
  sh -c 'find /data/uploads /data/private -type f | wc -l'
```

В карточке отмечают, какие категории вообще хранит контур, и какие
из них относятся к этому событию по мнению разработчика приложения
и юриста:

- учётные записи и согласия;
- контакты, заявки и переписка;
- приглашения в роли;
- файлы, фото и вложения на томе `anyq-data`;
- иные коллекции из подсчёта, если в них есть сведения о людях.

Имена, адреса и образцы значений не переписывают даже в закрытую
карточку, если для решения собственника хватает категории и числа.
Список конкретных субъектов, если он юридически необходим, юрист
хранит отдельно от репозитория и от канала инцидентов.

### Смена секретов приложения

Секреты создают на сервере и пишут только в `deploy/.env`
(права `600`). В чат, карточку и git их не вставляют.
Оценку категорий заканчивают до смены пароля базы: после смены
старый пароль в `deploy/.env` уже не подойдёт, пока файл не обновят.

Новый `JWT_SECRET` (не короче 32 символов):

```bash
umask 077
openssl rand -base64 48
```

Значение вписывают в `JWT_SECRET` на сервере. Старые сессии после
пересоздания API перестают действовать.

Пароль базы меняют интерактивно, без пароля в командной строке.
Образ Postgres читает `POSTGRES_PASSWORD` при первом создании тома
и сам пароль роли при смене файла не обновляет. Сначала роль, потом файл.

```bash
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml exec postgres \
  psql --username anyq --dbname postgres
```

В сессии `psql` выполните `\password anyq` и выйдите.
Затем впишите тот же пароль в `POSTGRES_PASSWORD` и в пароль внутри
`DATABASE_URL`. Сгенерировать его можно так (вывод сразу в файл,
не на экран чата):

```bash
openssl rand -base64 32
```

Проверка и пересоздание API:

```bash
chmod 600 deploy/.env
./deploy/check_env.sh
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml up -d --force-recreate --no-deps api
```

Ожидаемая последняя строка проверки: `Environment file is valid.`

Если файл ключа деплоя или `deploy/.env` могли покинуть сервер,
IT/MLOps выпускает новую пару SSH для пользователя `deploy` и
заменяет секрет `DEPLOY_SSH_KEY` в настройках репозитория.
Старый публичный ключ убирают из `authorized_keys`. Сам ключ
в карточку не пишут.

Если координатор и разработчик приложения считают, что затронуты
приглашения, SQL-разработчик отзывает неиспользованные. В выборку
не попадают хеш токена и названия компаний. Время — в том виде,
в каком приложение пишет `created_at` (UTC, секунды, суффикс `+00:00`).

```sql
UPDATE invitations
SET revoked_at =
  to_char(
    clock_timestamp() AT TIME ZONE 'UTC',
    'YYYY-MM-DD"T"HH24:MI:SS'
  ) || '+00:00'
WHERE used_at IS NULL
  AND revoked_at IS NULL;
```

В карточку пишут только число обновлённых строк.

Caddy включают снова только после смены `JWT_SECRET`, проверки
здоровья и записи координатора:

```bash
docker compose --env-file deploy/.env \
  -f deploy/docker-compose.prod.yml up -d caddy
```

### Решение собственника об уведомлении

Координатор в орган не пишет и срок не сдвигает.

1. SQL-разработчик передаёт собственнику и юристу категории и числа, без строк с людьми.
2. Юрист определяет, является ли событие нарушением безопасности персональных данных, и какое из двух записанных времён считать моментом обнаружения.
3. Собственник принимает решение об уведомлении уполномоченного органа.
4. Срок этого решения и отправки, если отправка нужна, — один рабочий день. Ориентир: Закон Республики Казахстан от 21 мая 2013 года № 94-V «О персональных данных и их защите», статья 25, пункт 2, подпункт 8. При нарушении безопасности персональных данных уполномоченный орган уведомляют в этот срок и указывают контакт лица, ответственного за организацию обработки, если такое лицо назначено.
5. В том же подпункте есть и другие действия одного рабочего дня. Нужны ли они этому событию, решает юрист. Этот регламент список закона не заменяет.
6. Если юрист считает, что обязанность уведомлять не наступила, собственник всё равно записывает это решение и краткую причину в закрытой карточке в тот же срок.

Проект уведомления заполняют вне репозитория. В тексте репозитория
остаётся только пустая форма. Реальных имён и телефонов здесь нет.
Контакт ответственного в момент отправки берётся из закрытого
источника и в git не копируется.

```text
Кому: уполномоченный орган в сфере защиты персональных данных
Канал подачи: <канал-уполномоченного-органа>
От: <наименование-собственника>
Момент обнаружения (Asia/Almaty): <ГГГГ-ММ-ДД ЧЧ:ММ>
Контакт лица, ответственного за организацию обработки:
<контакт-ответственного-за-обработку>
Суть: обнаружено нарушение безопасности персональных данных
в сервисе Anyq.
Категории субъектов: <категории-без-имён>
Категории данных: <категории-без-значений>
Числа строк по категориям: <только числа>
Что сделано: внешний вход останавливали, журналы сохранены
в Казахстане, секреты приложения сменены.
Решение собственника: <уведомить или не уведомить>
Краткая причина, если юрист считает уведомление не требующимся:
<причина-без-персональных-данных>
```

## Проверка

```bash
docker inspect -f '{{.State.Health.Status}}' anyq-api
docker inspect -f '{{.State.Health.Status}}' anyq-caddy
curl -fsS "https://<домен>/health"
curl -fsS "https://<домен>/healthz"
```

Ожидание после разрешения включить Caddy: `healthy` и `"ok":true`.
Пока Caddy остановлен, внешний `curl` не обязан проходить. Это
записывают в карточку как ожидаемое состояние изоляции, а не как
новый сбой.

Отдельно проверьте три факта и отметьте их в карточке:

- в канале нет секретов, журналов и персональных данных;
- `deploy/.env` имеет права `600`, а `./deploy/check_env.sh` печатает `Environment file is valid.`;
- решение собственника об уведомлении записано, и от него до момента обнаружения, который назвал юрист, не больше одного рабочего дня.

## Коммуникации

Внешнее письмо пилотному клиенту готовит координатор, текст смотрит
юрист, отправляет решение собственник. Шаблоны «видим сбой»,
«доступ восстановлен» и «разбор» — в [`docs/runbooks/comms.md`](comms.md).

Пока собственник не решил, что говорить о персональных данных,
нельзя отправлять письмо «доступ восстановлен» и нельзя писать,
что данные не затронуты. Допустимо короткое подтверждение, что
обращение получили и что ответ будет в рабочие часы
(Asia/Almaty, UTC+5).

Уведомление уполномоченного органа — не это письмо. Его форма выше.
Клиенту её не пересылают целиком.

## После инцидента

1. Закройте карточку только после проверки и после записанного решения собственника.
2. Разбор — по [`docs/incidents/POSTMORTEM.md`](../incidents/POSTMORTEM.md), без имён субъектов и без секретов.
3. Новый `deploy/backup.sh` запускают после закрытия изоляции, чтобы свежая копия лежала в Казахстане и не смешивалась со следами.
4. Заполненную форму уведомления в репозиторий не добавляют.
